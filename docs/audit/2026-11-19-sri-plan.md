# Plan: Subresource Integrity (SRI) for the embed snippet

## Why
A copied embed snippet loads `https://sombra.sh/embed/sombra-player.<version>.umd.js` into **someone else's page**, with full access to that page. If sombra.sh, its GitHub Pages deploy, or the DNS were ever compromised, every embedder would run attacker code. An `integrity="sha384-..."` attribute makes the browser refuse any file whose bytes differ from the ones the snippet was generated with, for every snippet copied *before* a compromise.

## What the code already gives us
- The loader (`buildSnippets` in `src/embed/publish.ts`) creates the script with `document.createElement("script")`, so `integrity` and `crossOrigin` can be set before it is appended.
- The live player is served with `access-control-allow-origin: *` (checked), which SRI requires for a cross-origin script.
- Filename is version-pinned (`src/embed/version.ts`), and the build is reproducible: my local build and CI's deployed file have the same sha256.

## The catch that shapes the design
SRI is only safe if **bytes behind a filename never change**. PR #8 changed the player's bytes while the name stayed `0.1.0`; with SRI that would silently break every embedder's snippet. So the real deliverable is the rule **"a different player build must have a different version"**, enforced by a gate, not just an attribute.

## Design
1. **Committed hash registry** `src/embed/integrity.json`: `{ "0.1.0": "sha384-..." }`. Reviewed in PRs like any code. Only the editor half imports it (`publish.ts`); the player bundle never does (import boundary unchanged).
2. **`scripts/embed-integrity.ts`**: reads `dist/embed/<PLAYER_FILENAME>`, computes sha384; `--write` adds/updates the entry for the current version, default mode only checks.
3. **Gate `verify:embed-integrity`** (needs a built `dist/`): fails when the registry has no entry for the current version, or the built bytes do not match it ("player bytes changed: bump EMBED_VERSION and run embed:integrity --write"). Runs in `deploy.yml` and `ci.yml` right after the build, so a deploy that would break embedders cannot publish.
4. **Snippet**: the loader gains `i.integrity="sha384-...";i.crossOrigin="anonymous";i.onerror=function(){console.error("Sombra player failed to load (integrity or network)")}`. Set before `appendChild`. If the registry has no entry (local dev build), the attributes are omitted and a code comment says why; production builds are guaranteed an entry by the gate.
5. **Docs**: `EMBED.md` (the immutability rule, how to release a new player version), `version.ts` comment.

## Tests (each paired with a control, mechanism asserted)
- **Offline** (`verify:embed-snippets` extended): snippet contains the integrity value equal to the registry entry and `crossOrigin`; control: no entry gives a snippet without them.
- **Gate mutations**: append one byte to the built player -> gate fails; delete the registry entry -> fails; change snippet to a wrong hash -> offline check fails.
- **Real browser, both directions** (the check that proves the browser enforces it): a local page loads the live `https://sombra.sh` player with (a) the correct hash -> player mounts, (b) one character wrong -> script blocked, console shows the digest error, nothing mounts. Run once now and once after deploy.

## Decisions needed from you
- **D1 - version.** (A, recommended) Register the current bytes as `0.1.0` and keep the name: no churn, `www`'s vendored copy and existing embeds are untouched; the *next* change forces a bump. (B) Bump to `0.2.0` in the same PR so "everything from 0.2.0 is immutable" starts clean; costs a coordinated change with the `www` session. Also settles the open "embed version bump" item.
- **D2 - failure behaviour.** (A, recommended) log a console error on load failure. (B) fall back to the sandboxed iframe snippet automatically (more code, more surface).

## Not in scope (note for later)
- Hosted scene files (`data-sombra-src`) are fetched with `fetch()`, which also supports an `integrity` option; a `data-sombra-integrity` attribute is a possible follow-up.
- An attacker who controls sombra.sh **and** the editor can mint snippets with their own hash; SRI protects snippets copied before the compromise, which is the realistic case. Registrar 2FA / DNS lock remain the first line of defence.

## Steps and size
About 7 small steps, one PR, no subagents: registry + script (1), gate + workflow wiring (2), snippet change + offline checks (3), mutation-test the gates (4), browser both-direction test (5), docs (6), PR + Core sign-off + post-deploy re-check (7). The only risk to existing users is none: snippets already in the wild have no hash and keep working.
